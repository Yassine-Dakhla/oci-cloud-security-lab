Building an internet-facing service with defense in depth.

The goal was not simply to make a webpage load. The project was built to understand what happens between an internet request and the application, then reduce unnecessary exposure at every layer.

Cloud networking

The environment uses a dedicated VCN with a 10.0.0.0/16 address range, a public subnet for the current server and a private subnet reserved for future internal services. OCI Security Lists form the first ingress control layer.

Linux hardening

  • SSH public-key authentication enabled.
  • Password authentication disabled.
  • Direct root SSH login disabled.
  • Unused rpcbind service disabled after confirming no NFS dependency.
  • Automatic security updates enabled.
  • Fail2Ban SSH jail enabled.

Container isolation

The Docker web container is published only as 127.0.0.1:8080:80. This means the application port is not intentionally reachable directly from the internet. Public traffic goes through the host Nginx reverse proxy instead.

TLS

HTTPS is terminated by host Nginx using a Let's Encrypt certificate. Certificate renewal was tested successfully with Certbot's dry-run workflow before being documented as complete.

External validation

22/tcp    open       ssh
80/tcp    open       http
443/tcp   open       https
8080/tcp  filtered   http-proxy

The important result is that the intended public services are reachable while the Docker application port remains filtered externally.

What made this project useful

The strongest lesson came from troubleshooting. Port 80 remained filtered even after it was allowed in OCI and Nginx was listening locally. Inspecting the host rules revealed an OCI Ubuntu iptables reject rule taking effect before UFW-managed chains. The fix required understanding rule order rather than simply adding another firewall rule.
